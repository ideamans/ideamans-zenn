弊社（アイデアマンズ）はページスピード改善の仕事で、主にフロントエンドの改善を提案しています。速くするためにHTMLやCSS、JavaScriptへ手を入れますが、見た目が変わってしまっては困ります。速くなっても表示が崩れるのでは意味がありません。

以前はこの確認を目視でしていました。ところが改善の試行錯誤をAIエージェントへ任せるようになり、人間の目視では追いつかなくなりました。

この記事では、AIの試行錯誤のループに「見た目が変わっていないか」の検査を組み込んだときの設計判断を整理します。検査の判定をLLMに任せなかった理由と、機械的な比較を実用にするための2つの工夫が中心です。

![AIにWebフロントエンドの見た目に関する回帰テストの目を与えるOSS page-regression-tester](https://notes.ideamans.com/ogp/2026/page-regression-tester.jpg)

## 検査の基本形：改変の前後で撮って比べる

やっていることは単純です。改変前のページをキャプチャし、改変後にもう一度キャプチャして2枚を比較します。弊社ではこれを page-regression-tester というツールにまとめ、MITライセンスで公開しています。

```bash
npm install -g page-regression-tester
npx playwright install chromium
```

```bash
# 改変前のキャプチャ
page-regression-tester capture https://example.com -o before.png

# （ここでAIエージェントがフロントエンドを改変する）

# 改変後のキャプチャ
page-regression-tester capture https://example.com -o after.png

# 2つを比較
page-regression-tester compare before.png after.png -o ./diff/
```

AIエージェントには、改変のたびにこの手順を踏ませます。比較の結果を見れば、改変が見た目に副作用を出していないかを確かめられます。

## 判定をLLMに任せなかった理由

最初は、見た目が変わったかどうかの判断自体もLLMに任せてみました。

ところが判断の揺らぎが大きく、使えませんでした。重要な副作用があっても「誤差の範囲です」と見逃してしまうことがあったのです。

改変を試すのも成否を判定するのもLLMでは、検査そのものが気まぐれになります。試行錯誤はAIに任せても、検査は機械的な方法にしたほうがよいというのが弊社の結論です。

## 素朴な比較が使えない理由

ただしキャプチャしてピクセルを突き合わせるだけでは実用になりません。何も変えていないのに差分が出てしまうからです。原因は2つあります。

- WebページにはJavaScriptやCSSアニメーションによる動きがある
- アンチエイリアス処理などで、毎回ピクセルパーフェクトなキャプチャが得られるとは限らない

下の画像は、デモ用のECサイトを異なるタイミングで2回撮影して比べた例です。左が1回目、右が2回目で、中央は変化した箇所を赤く示した差分です。

![同じページを異なるタイミングで2回撮影した比較画像。左がベースライン、中央が差分ハイライト、右が2回目の撮影](https://notes.ideamans.com/2026/static-webshot/diff.png)

改変していなくても差分が出るなら、検査は誤検知だらけになります。そこで工夫を2つ入れています。

1. キャプチャでは、画面上の動的な変化を抑える
2. 比較では、多少の「遊び」を持たせる

## 工夫1：動きを止めて撮る

キャプチャの段階で、ページの動きをできるだけ止めます。完璧ではありませんが、主に次のような手当てで多くのアニメーションを抑えられます。

- CSSのアニメーションとトランジションを`!important`で無効化する
- `Date.now()`や`Math.random()`、`performance.now()`を固定値にする
- `IntersectionObserver`を上書きし、遅延読み込みをすぐに発火させる
- 主要なカルーセルライブラリの自動再生を止め、最初のスライドで固定する

これで、ファーストビューにカルーセルがあるページでも、毎回ほぼ同じキャプチャが得られます。抑制の詳しい手法は、同じ仕組みを持つstatic-webshotというツールの記事に書いています（末尾のリンク参照）。

## 工夫2：SSIMで遊びを持たせて比べる

それでも残る細かな揺らぎを、比較の側で吸収します。ここで使っているのがSSIM（構造の類似性を測る指標）です。人間の視覚認知に近い感覚で、2つの画像の差分の大きさを定量化するアルゴリズムです。弊社では、画像の軽量化でどれだけ劣化したかを測る場面でも使っています。

```bash
page-regression-tester compare before.png after.png --method pixel,ssim -o ./diff/
```

SSIMは、アンチエイリアスのような小さな揺らぎは見逃しつつ、レイアウトが崩れるような大きな構造の不一致は検出します。

ピクセル単位の比較と併用できるので、役割を分けると読みやすくなります。

| 比較方法 | 見るもの |
|---|---|
| ピクセル比較 | どこが違うか（ヒートマップ） |
| SSIM | どのくらい違うか（スコア） |

## まとめ

- 速くなっても表示が崩れては意味がないので、フロントエンド改変の前後で見た目を検査している
- AIに試行錯誤を任せると目視では追いつかないため、キャプチャの比較で機械的に検査するようにした
- 判定までLLMに任せると「誤差の範囲です」と副作用を見逃すことがあった
- 機械的な比較を実用にするには、キャプチャで動きを止め、比較ではSSIMで遊びを持たせる

試行錯誤をAIに任せるほど、その結果を判定する側は揺らがないものにしておく必要があります。弊社はその役割を、キャプチャを機械的に比べる仕組みに持たせました。
