「レンダリングブロックを解消しましょう」という指摘は、Lighthouseを回せば誰でも一度は目にします。ただ、`defer` を付けるか `async` にするか、あるいは位置を動かすか。いざ選ぶ段になると、根拠を持って判断できていないことは意外と多いものです。

この記事は、その判断を **仕組みから** できるようにするためのものです。まず同期scriptがなぜHTMLパースを止めるのかを押さえ、そのうえで `defer` / `async` / 位置移動 / インライン分割の使い分けを、実在の国内サイトの計測とともに整理します。対象読者はフロントエンドの表示速度を触るエンジニアです。

## ブラウザはscriptタグの前で立ち止まる

ブラウザはHTMLを上から順に読みながら、次に取得すべきリソースを判断していきます。この途中で、`async` や `defer` が付いていない `<script>` タグに出会うと、処理が止まります。スクリプトのダウンロードと実行が終わるまで、HTMLの解析は先に進みません。

![ブラウザがHTMLパース中に同期スクリプトと出会うと、ダウンロードと実行が終わるまでパースが止まる](https://notes.ideamans.com/posts/2026/render-blocking-scripts/parse-block-flow.png)

順番にすると、こうなります。

1. HTMLのパースを停止する
2. スクリプトをダウンロードする（外部ファイルの場合）
3. スクリプトを実行する
4. 実行が完了したらHTMLのパースを再開する

なぜブラウザはわざわざ止まるのか。それは、スクリプトが `document.write()` などでDOMを書き換える可能性があるからです。パースを進めた先が書き換えで無効になるかもしれない以上、実行が終わるまで待つのが安全、という設計になっています。

### `<head>` に置くと影響が大きい

同じ同期scriptでも、`<head>` に置かれると影響が大きくなります。CSSの読み込みやレンダリングツリーの構築より前にブロックが起きるため、**スタイルの適用と描画が、スクリプトの完了を待たされる** からです。FCP（First Contentful Paint）が直接遅れます。

### プリロードスキャナも助けにならない

近年のブラウザには、メインのパーサーとは別に、先回りしてリソースを見つける「プリロードスキャナ」があります。これは通常、後続の画像やCSSを早めにダウンロードし始めてくれる頼もしい仕組みです。

ところが同期scriptのブロック中は、この先回りが効きにくくなります。パーサーが止まっている以上、その先のDOMはまだ確定しておらず、プリロードスキャナが安全に取得できるものは限られます。「ブロックしている間に裏で他を進めておく」が期待ほど働かない、というのがやっかいなところです。

### 外部ドメインからの読み込みは遅延が複合する

スクリプトを外部ドメインから読み込んでいる場合、話はさらに重くなります。ダウンロードを始める前に、DNSの解決とTLS接続の確立が必要だからです。この接続コストが、まるごとHTMLパースのブロック時間に上乗せされます。

## 実在サイトで測るとどう出るか

仕組みだけでは、影響の大きさが実感しづらいものです。弊社の[表示速度ボトルネック実例研究（vigilante）](https://vigilante.sitespeed.info/)から、パターンの異なる例をいくつか挙げます。いずれもボトルネックを1つだけ取り除いたシミュレーション値です。

**外部CDNからの同期jQueryがFCPを1.3秒押し下げた例。** ある旅行メディアでは、`<head>` の最初の `<script>` が外部CDNから同期でjQueryを読み込んでいました。DNS解決とTLS接続の待機が約300〜500msあり、その間パースが止まります。このリソースを同一ドメイン配信に切り替えるシミュレーションで、FCPが2.0秒から0.7秒へ短縮されました。接続コストがそのままブロック時間になっていた、とわかる数字です。

**総合スコア96の高水準サイトでも残っていた例。** ある新聞社のトップページは、観測時点でLCP 0.3秒と非常に速い状態でした。それでも `<head>` に同期scriptが3件残り、合計約23msのブロックが発生していました。実装品質が高くても、この種のブロックは残ります。特別なサイトの話ではありません。

**インラインscriptの肥大化でHTMLが重くなっていた例。** あるECサイトでは、サイト内検索用の全商品データ（約703KB）などがインラインscriptとしてHTMLに直接埋め込まれ、HTMLサイズが約1.94MBに達していました。初期表示に不要なこれらを外すと、HTMLは約半分になり、LCPが0.2秒改善しました。同期scriptの問題は、外部ファイルだけでなくインラインにも及びます。

## どう直すかを、判断として整理する

対処は「属性を付ける」か「位置を動かす」の2系統です。どれを選ぶかは、そのスクリプトの性質で決まります。

### `defer`：実行順序が重要なスクリプト

```html:defer
<!-- 変更前（同期） -->
<script src="app.js"></script>

<!-- 変更後 -->
<script src="app.js" defer></script>
```

`defer` は、ダウンロードをHTMLパースと並行して行い、**パース完了後に記述順で実行** します。順序が保たれるので、ライブラリとそれに依存するコードのように、実行順が重要なスクリプトに向いています。迷ったらまず `defer` を検討する、くらいの位置づけです。

### `async`：他に依存しないスクリプト

```html:async
<script src="analytics.js" async></script>
```

`async` は **ダウンロードが終わり次第すぐ実行** します。順序は保証されません。解析タグや広告タグのように、他のスクリプトと依存関係のない単独で完結するものに向いています。

依存があるスクリプトに `async` を付けると、実行順が崩れて動かなくなることがあります。付ける前に「これは本当に単独で動くか」を静的解析などで確かめるのが安全です。実際、あるオンラインストアでは、body末尾の未依存スクリプト3件に `async` を付けるシミュレーションで、レイアウトのずれ（CLS）が0.383から0.209へ改善しました。実行タイミングのずれが、結果的に安定性に効いた例です。

### 位置を動かす：属性を触りにくいとき

`defer` / `async` を付けると挙動が変わってしまうスクリプトや、テンプレートの都合で属性を足しにくいときは、`<head>` から `</body>` の直前へ移すだけでもブロックを避けられます。

```html:move-to-body-end
<head>
  <!-- ここから同期scriptを外す -->
</head>
<body>
  <!-- コンテンツ -->
  <script src="heavy.js"></script>
</body>
```

HTMLのパースを先に終わらせられるので、FCPの改善につながります。

### インラインは「初期表示に要るか」で切る

初期表示に不要な大量データをインラインで埋め込んでいるなら、必要になった時点で非同期取得する形へ切り替えます。

```js:lazy-fetch
// 検索が必要になったときに初めてデータを取得する
async function initSearch() {
  const res = await fetch('/api/products.json')
  window.ALL_PRODUCTS = await res.json()
}
```

HTMLの転送量そのものが減るので、ドキュメントのダウンロード完了が早まります。

判断を1枚にまとめると、次のようになります。

| スクリプトの性質 | 選ぶ対処 |
|---|---|
| 実行順序が重要 | `defer` |
| 他に依存しない | `async` |
| 属性を触りにくい | body末尾へ移動 |
| 初期表示に不要な大量インライン | 非同期取得に切り替え |

## 手元で確認する

直したい箇所を見つけるには、次の2つが手軽です。

- **Chrome DevToolsのPerformanceタブ。** リロードして記録すると、`Parse HTML` の最中に `Evaluate Script` が割り込んでいる箇所が見える。そこが同期scriptによるブロック
- **Lighthouse。** 「Eliminate render-blocking resources」の指摘に `<script>` タグが含まれていれば、それが対象

## まとめ

- 同期scriptは、DOM書き換えの可能性ゆえにHTMLパースを止める。`<head>` に置くと描画開始（FCP）が直接遅れる
- ブロック中はプリロードスキャナの先回りも効きにくく、外部ドメインなら接続コストがブロック時間に上乗せされる
- 対処は「属性」か「位置」。実行順が重要なら `defer`、単独なら `async`、触りにくければbody末尾へ移動、肥大インラインは非同期取得へ
- 実装品質が高いサイトでも残るパターンなので、仕組みを押さえて判断できるようにしておくと応用が効く
