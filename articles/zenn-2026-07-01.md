長く運用してきた広報ブログを、Movable Type から VitePress へ移し替えました。AWS上の Movable Type AMI版で動かしていた約268記事を、VitePress と GitHub Actions による静的サイトへ載せ替える作業です。

きっかけは普段の開発環境が Cursor に寄ったことでした。記事やテンプレートをエディタの中で完結させたくなり、構成をまるごと見直しました。

効果は明快でした。サイト全体の再構築にかかる時間が、1分41秒から5.66秒に縮みました。差分ではなく全記事を作り直しても5秒台で終わるので、書いて確かめるまでの待ち時間がほぼ消えます。

![移行後のアイデアマンズ広報ブログのトップページ](https://assets.ideamans.com/miyanaga/images/2025/05/ideamans-blog-webpage.png)

この記事では、なぜ VitePress を選んだのか、そしてドキュメント向けの VitePress をブログCMSとして使うために越えた壁を、順に書いていきます。

## 静的サイトに寄せたい理由

前提として、複雑な要件がないなら静的コンテンツをシンプルなWebサーバーで配るのが望ましいと考えています。

プログラムの都合でサイトが壊れずに済み、その分だけ運用コストが下がります。表示も素直に速くなります。広報ブログにはこの軽さがちょうど合います。

問題は、Movable Type の柔軟なアーカイブを捨てずに静的サイトへ移れるかでした。

## 3つの候補で迷った

最初に検討したのは Astro です。AstroWind というテンプレートが秀逸で、これを使いたい気持ちが強くありました。

ところが約268記事を Markdown で書き出してビルド性能を試すと、完了まで1分半ほどかかりました。使い方を誤っていた可能性はありますが、1記事を直すたびにこの時間が乗るのは厳しいと判断しました。

次に考えたのが Movable Type の継続です。記事更新だけなら差分ビルドがすぐ終わるので、268記事の規模では差分が要ると思い込んでいました。

ただ Movable Type にはアセットパイプラインがありません。最適化したCSSやJavaScriptを別のデザインシステムで用意し、テンプレートから参照する形になります。デザインシステムとテンプレートの二重管理は、始める前から気力をそがれました。

最後に VitePress で268記事のビルドを試したところ、2.56秒で終わりました。Astro の結果で勘違いしていましたが、いまどき268記事はデータとして決して多くありません。差分ビルドという発想自体が不要でした。

Vite によるアセットパイプラインがあり、ビルドも速い。あとはアーカイブを再現できるかどうかで、ここを手探りで詰めて採用に至りました。

## Layout.vue でテンプレートを切り替える

CMSはふつう、トップページ、記事詳細、記事一覧といった複数のテンプレートを持ちます。VitePress でこれをどう表すかが最初の勘所でした。

素のVueなら `vue-router` を使うところですが、VitePress はもっとラフです。`.vitepress/theme/Layout.vue` が全体のテンプレートを司り、その中でURLパスを見てコンポーネントを切り替えます。

```vue
<script setup lang="ts">
import { useRoute } from 'vitepress'
// route はURLパス情報を持つので、これで条件分岐する
const route = useRoute()
</script>

<template>
  <Home v-if="トップページのパス条件" />
  <List v-else-if="一覧ページのパス条件" />
  <Article v-else-if="詳細ページのパス条件" />
  <NotFound v-else />
</template>
```

パスごとに描画するコンポーネントを差し替えるだけで、CMSのテンプレート管理に近い形を組めます。発想がわかれば、ここはむしろ素直でした。

## カテゴリや著者は data ローダーで供給する

VitePress では Markdown ファイルが記事データに対応します。ですがブログには、カテゴリや著者のように記事本文とは別のデータも要ります。

これは `.vitepress/theme` に `.data.ts` ファイルを置く作法で供給できます。ビルド時にデータを読み込み、コンポーネントへ渡す仕組みです。たとえばカテゴリ一覧は `categories.data.ts` から供給しました。

ひとつ手こずったのが、後述するRSS生成スクリプトとの共有です。`genFeed.ts` から `categories.data.ts` をそのまま使う形が、思ったとおりには動きませんでした。

そこで実データは素の `categories.ts` に置き、`categories.data.ts` と `genFeed.ts` の双方からこれを読む構成にしました。`.data.ts` ひとつにまとめる方法もありそうでしたが、今回は見つけられず、データ本体を切り出して両取りしました。

## ダイナミックルートとパスのリライトでアーカイブを再現する

いちばん悩んだのがURLの構造です。検索エンジンにインデックスされた履歴を捨てたくなかったので、Movable Type 時代のパス構造をそのまま残したい意図がありました。

VitePress は Markdown とURLが自動で1対1に対応します。それ以外のルートを足すには、ダイナミックルートとパスのリライトを組み合わせます。

ダイナミックルートは、配列データをもとに仮想的な Markdown を展開する機能です。実ファイルは存在しないのに、対応するルートが生成されます。これでカテゴリ別や年月別のページを用意できます。

![VitePressのカスタマイズでブログのアーカイブを再現した広報ブログ](https://notes.ideamans.com/ogp/2025/blog-renewal.jpg)

ただしダイナミックルートが作るのは、あくまでフラットな仮想ファイル群でした。`/2025/04` や `/2025/05` のような階層は、これだけでは表せません。

そこでパスのリライトを重ねます。リライトは Markdown のパスに対して、実際に出力するパスをマッピングする仕組みです。年月アーカイブなら、まずダイナミックルートを次のように置きます。

```text
.
└─ monthly
   ├─ [year]-[month].md
   └─ [year]-[month].paths.js
```

そのうえで `config.ts` のリライトで、フラットなパスを階層パスへ写します。

```javascript
{
  rewrites: {
    'monthly/:year-:month.md': ':year/:month/index.md'
  }
}
```

ダイナミックルートで仮想ファイルを生み、リライトで階層へ写す。この2段で Movable Type のアーカイブをおおむね再現できました。

## MPAモードを明示する

ひとつ落とし穴がありました。VitePress は静的サイトジェネレーターですが、画面遷移にはSPA的な挙動も持ちます。

ビルドしたHTMLには多くのJavaScriptが埋め込まれ、静的Webサーバーに置くと、特にダイナミックルートへの遷移で表示の崩れが起きました。

対処は `defineConfig` に `mpa: true` を渡すことです。SPAではなく複数ページからなるMPAだと明示すると、ページ遷移が正常に戻りました。ダイナミックルートを多用するブログでは、この一行が効きます。

## RSSは buildEnd フックで生成する

VitePress 自体にRSS生成の機能はありません。そこで簡易なスクリプトを `.vitepress/genFeed.ts` に用意し、`config.ts` の `buildEnd` フックで起動するようにしました。

ビルドが終わった直後にフィードを書き出す流れです。この組み方は Vue.js 公式ブログのやり方に倣いました。公式が同じ `genFeed.ts` 方式を採っているので、迷ったときの拠りどころになります。

## 移行を終えて

VitePress とその前身の VuePress は長く使ってきましたが、ドキュメントサイトの域を出ず、ここまで作り込んだのは初めてでした。

Layout.vue でのテンプレート切り替え、`.data.ts` によるデータ供給、ダイナミックルートとパスのリライト、`buildEnd` でのRSS生成。この4つを押さえれば、ドキュメント向けの VitePress も十分にブログCMSとして使えます。

そして再構築が5.66秒で終わる軽さは、書く動機そのものを底上げします。好みのCMSをまたひとつ手に入れた感覚で、これからのLP制作やサイト展開にも積極的に使っていくつもりです。
