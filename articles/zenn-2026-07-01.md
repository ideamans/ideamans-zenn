サイトの表示スピードを改善するとき、いちばん確実なのは実際に変更して計測してみることです。ところが本番環境に手を入れて計測するのは、できれば避けたいところです。施策が外れたら戻す、また試す。この往復を本番でやるのは怖いものです。

そこで弊社（アイデアマンズ）は、本番サーバーへ触れずに同じ検証を何度でも繰り返せる仕組みを OSS として公開しています。`http-playback-proxy` という Rust 製のツールです。

https://github.com/ideamans/rust-http-playback-proxy

この記事では、このツールが「Webページのほぼ完全なコピー環境」をどう作るのかを、記録・再生・編集の仕組みに沿って解説します。スピード改善の検証環境に悩んでいる方や、VCR 系ライブラリをページ全体に広げたらどうなるかに興味がある方に向けた内容です。

## なぜ「コピー環境」が要るのか

スピード改善のために検証用の開発環境を用意しようとすると、これが意外と重い作業になります。

静的サイトならまだしも、データベースと連携した動的サイトや、複雑なインフラ構成のサイトでは、環境の再現そのものが技術的な課題になります。社外の専門家に相談する場合は、環境や情報の共有がボトルネックにもなります。

ここで発想を変えます。スピード改善で見たいのは、ブラウザがページを表示するまでの一連の通信です。バックエンドのアプリケーションそのものではありません。だとすれば、その通信だけを丸ごと記録して再生できれば、サーバーがなくても表示は再現できるはずです。

## HTTPプロキシのおさらい

`http-playback-proxy` は名前のとおり HTTP プロキシの一種です。

HTTP プロキシは、ブラウザとサーバーの間に立つ中継サーバーです。ブラウザや OS にはプロキシを指定する標準の仕組みがあり、設定すればすべての通信が指定したサーバーを経由するようになります。企業ネットワークのアクセス制御やキャッシュ、開発時のデバッグなどで広く使われています。

このツールが普通のプロキシと違うのは、「記録」と「再生」という2つのモードを持つ点です。順番に見ていきます。

## 記録モード：ページ表示の全通信をキャプチャする

![記録の仕組み。ブラウザとサーバーの間に立ち、全通信を監視してファイルに記録する](https://notes.ideamans.com/assets/recording.pHxjn1OZ.png)

記録モードでは、ブラウザのプロキシに `http-playback-proxy` を指定し、普段どおりにページを閲覧します。プロキシはブラウザとサーバーの間に立ち、すべての通信を監視します。

このとき記録するのはレスポンスのデータだけではありません。次の3種類をまとめて保存します。

- レスポンスボディ（HTML・CSS・JavaScript・画像などのコンテンツ）
- HTTPヘッダー（Content-Type や Cache-Control などのメタ情報）
- タイミング情報（最初の1バイトが届くまでの遅延と、転送が完了するまでの時間）

3つめのタイミング情報が、後で効いてきます。

現代のWebページが単一のサーバーから配信されることは稀です。サードパーティのタグ、CDN、広告ネットワークなど、複数のサーバーからリソースを集めて1ページを構成しています。`http-playback-proxy` はこれらすべてのサーバーとの通信を記録するので、表示に必要なリソースが漏れなくそろいます。

:::message
TTFB（Time To First Byte）は、リクエストを送ってから最初の1バイトが返るまでの時間です。サーバーの応答速度やネットワーク遅延を反映する指標で、記録するタイミング情報のひとつです。
:::

## 再生モード：サーバーなしで「同じ表示」を再現する

![再生の仕組み。プロキシはサーバーに問い合わせず、記録から該当レスポンスを返す](https://notes.ideamans.com/assets/playback.CMJz9k-j.png)

再生モードでも、ブラウザは引き続き `http-playback-proxy` をプロキシとして使います。ただし今度はプロキシがサーバーへ問い合わせることはありません。

ブラウザからリクエストが来ると、プロキシは記録の中から該当するレスポンスを探し、記録しておいたタイミングに従って返します。あるリソースの取得に元々200msかかっていたなら、再生時も200ms待ってから返すわけです。これでスピード面まで含めて表示プロセスが再現されます。

ブラウザから見ると、実際のサーバーにアクセスしているのと区別がつきません。Lighthouse のようなスピード計測ツールも、普段どおりにこのページを計測できます。

エンジニアの方なら VCR 系のライブラリをご存じかもしれません。VCR は API のような単独の通信を記録・再生するものですが、`http-playback-proxy` はそれをブラウザのページ表示全体へ広げたものだと考えれば分かりやすいはずです。

## 記録データは「手作りの静的サイト」のように編集できる

このツールの特徴として、もうひとつ大きいのが記録データの編集しやすさです。

通常 HTTP レスポンスは圧縮されていたりミニファイされていたりします。そのまま保存しても人手では扱いにくいので、記録の時点で展開・整形しておきます。

- gzip や brotli などの圧縮を解いて保存する
- Shift-JIS など旧来の文字コードも UTF-8 に変換する
- ミニファイされた HTML・CSS・JavaScript を読みやすく整形する

結果として記録されたファイル群は、手作りの静的サイトのような構造になります。ファイルを開けば、普通の HTML や CSS として読み書きできます。

:::message
スピード改善の検証では、CSSの一部を削る、JavaScriptの読み込み順を変えるといった作業が頻繁に発生します。そのたびに圧縮やミニファイを解除していては効率が悪いものです。最初から編集しやすい形で保存しておくと、試行錯誤のサイクルを速く回せます。
:::

## 編集して再生し、効果を確かめる

![編集と再生。記録データを書き換え、再生に反映して計測する](https://notes.ideamans.com/assets/edit-and-playback.N5cbxG5g.png)

記録データは自由に編集でき、編集内容は次の再生に反映されます。つまり、こういう検証ができます。

- CSSの最適化（不要なスタイルを削ってサイズを減らす）
- JavaScriptの遅延読み込み（defer / async を付ける）
- 画像の軽量化（圧縮して差し替える）
- リソースの結合・分割（ファイルをまとめる、または分ける）

編集したら再生モードで Lighthouse などを走らせるだけで、その変更がスピードにどう効くかをすぐ確認できます。

ここまでの仕組みがもたらす利点は、大きく2つです。

ひとつは試行錯誤の速さです。ファイルを編集してすぐ計測でき、開発・デプロイ・計測という長い手順を踏まずに済みます。コピー環境の中でいくら実験しても本番サイトには一切手を加えないので、安全に何度でもやり直せます。

もうひとつは環境の再現が要らないことです。複製するのはフロントエンドの構成だけで、バックエンドのデータベースやアプリケーションサーバーは不要です。必要なのは記録したファイル群だけなので、チーム外との共有も容易です。

「やってみないとわからない」状態から、「効果を確認してから実装する」へ。検証のアプローチが一段変わります。

## まとめ

`http-playback-proxy` は、Webページの表示プロセスを丸ごと記録・再生して、精巧なコピー環境を作るツールです。

- 記録：ブラウザが表示する際の全通信を、タイミングまで含めてキャプチャする
- 再生：記録に基づき、サーバーなしでタイミングまで再現したレスポンスを返す
- 編集：記録データは静的サイトと同じ感覚で書き換えられる
- 検証：編集の効果を計測ツールで即座に確かめられる

以前は TypeScript で開発していましたが、現在はより高速かつ正確に動くよう Rust で書き直しています。MIT ライセンスの OSS として公開しており、Go や TypeScript からも利用できます。
