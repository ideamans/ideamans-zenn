弊社（アイデアマンズ）はページスピード改善の相談を受けて、主にフロントエンドの改善提案をしています。そこで重宝しているのが、Chromeの実ユーザーの表示速度を集計したChrome UX Report（CrUX）です。

CrUXは、計測タグを置いていないサイトでも過去の実測値が分かります。対象は世界中のサイトです。相談を受けたその場で長期の傾向（速くなっているのか遅くなっているのか）を調べられ、競合サイトとの比較も同じように出せます。

ただし、データを使うにはBigQueryかCrUX APIを操作しなければなりません。しかも入手先は2つに分かれていて、欲しいデータによって使い分けが要ります。

この記事では、その2つをAIエージェントから引けるよう1つのCLIへまとめたときに考えたことを書きます。対象は、CrUXを業務で使っている人とAIエージェント向けのCLIを設計している人です。

![BigQueryとAPIに分かれたCrUXのデータをAIエージェントから引くためのOSS CLI crux-cliのタイトル画像](https://notes.ideamans.com/ogp/2026/crux-cli.jpg)

## なぜCLIにしたか

AIエージェントにBigQueryやAPIを直接触らせることもできます。ただ、それだとクエリやリクエストの組み立てにコンテキストを多く使ってしまいます。

テーブルの構造を調べてSQLを書く作業や、APIのリクエストを組み立てる作業を毎回AIにやらせるとします。すると本題の「このサイトはどうなのか」へ入る前に、コンテキストが減っていきます。

そこで、入手先の違いはCLIの中で吸収することにしました。それが crux-cli（コマンド名は `crux`）で、MITライセンスで公開しています。

- [ideamans/crux-cli](https://github.com/ideamans/crux-cli)

## 2つの入手先の違い

crux-cliは入手先ごとにコマンドを分けています。

| | BigQuery | CrUX API |
|---|---|---|
| コマンド | `crux device` | `crux history`（週ごとの推移）/ `crux record`（最新） |
| 単位 | オリジン | オリジン、または特定のページ（URL） |
| 期間 | 月ごと。長い期間をさかのぼれる | 28日間の移動集計。`history` は最大40週 |
| 費用 | クエリ料金が自分のGoogle Cloudプロジェクトにかかる | 無料（APIキーだけで使える） |
| 指標 | LCP・CLS・INP・FCP・TTFB・OnLoad・RTT・FID | LCP・CLS・INP・FCP・TTFB・RTT |

特定のページの数字はAPIでしか取れません。反対に、OnLoadやFIDはBigQueryにしかありません。どちらを使うかは、何を知りたいかで決まります。

BigQueryで引ける月次の推移は、たとえば次のような形になります。ある通販サイトのLCP（75パーセンタイル）を、弊社の自前の計測と重ねたグラフです。

![ある通販サイトのLCP p75の月次推移。2025年8〜9月に約1.5秒から3.4秒へ急に悪化し、自前の計測とCrUXがほぼ重なって動いている](https://notes.ideamans.com/posts/2026/crux-vs-rum/trend-lcp-c.png)

APIの `history` は最大40週までなので、それより長く月ごとにさかのぼる比較はBigQueryで引くことになります。

## どちらで引くかはAIに選ばせる

コマンドを分けた以上、どちらを使うかを誰かが判断する必要があります。crux-cliでは、その判断をAIエージェントに任せています。

AI向けのリファレンスには、2つの入手先の違いと、使い分けの目安を書いてあります。

| 知りたいこと | 使うもの |
|---|---|
| 特定のページの数字 | API（`history` か `record`） |
| APIキーしかなく、Google Cloudのプロジェクトがない | API（`history` か `record`） |
| 長い期間の月ごとの推移や、多数のオリジンをそろえた月次比較 | BigQuery（`device`） |
| OnLoadやFIDが要る | BigQuery（`device`）のみ |

弊社でAIに頼むときは、どちらで引くかを気にしていません。知りたいことをそのまま伝えると、AIが次のようなコマンドを組み立てます。

```bash
# 「このサイトと競合2社の、スマホでの過去1年のLCPを比べて」
crux device -o https://example.com -o https://competitor-a.com -o https://competitor-b.com \
  -d phone --metrics lcp

# 「このページの最近の傾向を見て」
crux history -u https://example.com/products/ -d phone

# 「いまの状態だけ知りたい」
crux record -o https://example.com
```

出力は表・JSON・CSVから選べます。AIが結果を読むときはJSONを使います。

## BigQueryの料金を抑えるキャッシュ

`crux device` は、BigQueryのクエリ料金が自分のプロジェクトにかかります。AIに任せて何度も引かせるなら、ここは手当てが要ります。

crux-cliは、オリジンと期間の組ごとに結果を手元にキャッシュします。キャッシュにないものだけをBigQueryに問い合わせます。

CrUXは毎月中旬に新しい月のデータを公開します。そこで最新の月を1日1回確かめ、新しい月が出ていれば取り直すようにしました。複数のオリジンを比べるときも、問い合わせるのはキャッシュにないオリジンだけです。

## 数字の読み違いを防ぐ

コンテキストを節約しても、AIが数字を読み違えては意味がありません。そこでJSON出力の意味もリファレンスに書いています。

- 良好な体験の割合などは0から1の割合で表す。`0.83` は83%
- 75パーセンタイルの値の単位は、指標ごとに決まっている
- 割合や75パーセンタイルが `0` のときは、たいていデータが足りないことを表す

3つめは、値が `0` だからといって「速い」と読まないようにするための注意書きです。

## 準備

BigQueryを使うときは、Google Cloudの認証とプロジェクトの設定を一度だけ行います。

```bash
gcloud auth application-default login
crux auth set-project YOUR_GCP_PROJECT_ID
```

CrUX APIだけを使うなら、APIキーを登録すれば済みます。

```bash
crux auth set-api-key YOUR_CRUX_API_KEY
```

AI向けのリファレンスは `crux llm` で出てきます。2つの入手先の違い、全コマンドとフラグ、指標ごとの良好の基準、JSON出力の意味がまとまっています。

```bash
crux llm                  # Markdown
crux llm --format json    # 章ごとのJSON配列
```

## まとめ

- CrUXは計測タグなしで世界中のサイトの過去の実測値が分かり、長期の傾向や競合比較をすぐ示せる
- データはBigQuery（月次・オリジン単位）とCrUX API（28日の移動集計・ページ単位も可）に分かれる
- 両方を1つのCLIにまとめ、どちらで引くかの目安はAI向けのリファレンスに書いた
- BigQueryの料金は、オリジンと期間ごとのキャッシュで抑えている
- 割合の表し方や、値が `0` のときの意味まで書き、AIが数字を読み違えないようにしている
