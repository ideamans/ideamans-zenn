Core Web Vitalsの中で、INP（Interaction to Next Paint）だけは他の指標と性質が違います。

CLSやLCPはページの読み込みプロセスで計測されるため、Lighthouseで機械的にシミュレーションできます。改善案を思いついたらその場で試し、数字が動くかを確認できます。

ところがINPは、ユーザーがページ上で何らかの操作をして初めて計測されます。何の操作をするかはユーザー次第なので、読み込みプロセスのようなシミュレーションができません。試行錯誤による仮説検証が進めにくい指標です。

この記事では、INPの内訳を整理したうえで、シミュレーションできない指標をどう攻めるかを解説します。

## INPは3つの時間の合計

ユーザーがページを操作すると、JavaScriptで登録されたイベントハンドラが処理を行い、その結果ページの一部が描き変わります。この操作から画面に変化が現れるまでの時間がINPです。

内訳は3つに分かれます。

- **Input delay**: イベントハンドラが実行されるまでの待ち時間。操作の瞬間に他の処理が走っていれば、その完了待ちになる
- **Processing time**: イベントハンドラ自体の処理時間。1つの操作に複数のハンドラが登録されている場合もある
- **Presentation delay**: ハンドラ実行後から描画までの時間。DOMが変更されるとレイアウトが再計算され、結果が画面に反映される

この分解が重要なのは、**どこが長いかで打つべき手がまったく変わる**からです。

Input delayが長いなら、原因は操作した要素ではなく、その瞬間にメインスレッドを占有していた別の処理にあります。ページの読み込みからしばらくは、サードパーティスクリプトを含めたJavaScriptとブラウザ自身が大忙しになります。その間の操作は後回しにされがちです。

Processing timeが長いなら、ハンドラの中身が重いということです。実例としては、jQueryによる大量のDOM操作、要素の寸法取得によるレイアウトの即時計算、同期通信によるメインスレッドの占有といったものがありました。

Presentation delayが長いなら、DOMとCSSの規模が効いています。レイアウトの再計算は対象のDOMとCSSOMに基づいて行われるため、どちらも巨大だとそれだけ時間がかかります。

:::message
INPの対象になるのは、クリック・タップとキーボード操作です。最も頻繁に行われるスクロールは、実はページ操作に含まれません。ビューポートを移動しているだけで、言うなればウィンドウの操作だからです。
:::

## DevToolsで測る方法とその限界

INPはChrome DevToolsのPerformanceタブで計測できます。タブを開くとINPの表示欄があり、ページを操作すると直前の操作の値が表示され、履歴も残ります。

INPは元々値が小さく、高性能なPCではさらに短くなります。`CPU` の設定を `20x slowdown` などにすると、シビアに計測できます。

この機能の弱点は、ページ遷移の際のINPを計測できないことです。遷移をブロックすれば計測できるので、Consoleで次のスクリプトを実行しておきます。

```javascript
window.addEventListener('beforeunload', (e) => (e.returnValue = 'unload?'))
```

ただし、ここまでやっても本質的な壁が残ります。

INPの評価が悪いサイトで開発者ツールを使い、いろいろな操作を試しても、なかなか悪い数値が出ません。操作の選択肢は無数にあり、状況やタイミングにも左右されるため、実ユーザー環境と同じ遅さを再現できるとは限らないからです。まるで幽霊や素粒子を探すような作業になります。

## 憶測をやめて実ユーザーの内訳を集める

こういうとき、予測の精度を上げようとしてもそれは憶測にしかなりません。事実を計測するほうがはるかに確実です。

計測でおなじみの[web-vitals](https://www.npmjs.com/package/web-vitals)パッケージには **attribution build** というバリエーションがあり、指標の数値だけでなく、その根拠となる情報まで取得できます。弊社（アイデアマンズ）では、これを使ってページに `script` タグを1つ埋め込むだけでINPの詳細を収集し、BigQueryへ蓄積する仕組みを作りました。

取得できるのは次のようなデータです。

```json
{
  "inputDelay": 4.100000023841858,
  "interactionTarget": "#responsive-menu-button",
  "interactionType": "pointer",
  "loadState": "complete",
  "presentationDelay": 27.899999976158142,
  "processedEventEntries": [
    {
      "duration": 32,
      "entryType": "first-input",
      "name": "mousedown",
      "startTime": 1793.3999999761581
    }
  ],
  "processingDuration": 0
}
```

3つの時間の内訳に加えて、操作対象のDOM要素（`interactionTarget`）、操作の種別（`interactionType`）、そのときのページ読み込み状態（`loadState`）が分かります。

これが揃うと、判断が一気に具体的になります。

`loadState` が `loading` で `inputDelay` が大きければ、そのINPはページ読み込み時の高負荷に巻き込まれた結果です。この場合はTBT（Total Blocking Time）の改善がINPの改善につながる可能性が高いと言えます。`processingDuration` が大きければイベントハンドラに重い処理があり、`presentationDelay` が大きければDOMやCSSの規模に原因がある、と切り分けられます。

統計的に集まれば、「どの要素のどの操作が主要因か」まで絞り込めます。

:::message
TBTがINPに関係するとよく言われますが、注意が必要です。INPの遅延発生ポイントは3つあり、TBTはそのうちInput delayにしか関係しません。TBTを改善すればINPが良くなるという保証はありません。
:::

## Input delayが主因ならTBTを削る

内訳を見て、主因がInput delayだったとしましょう。実際、INPが悪い原因はイベントハンドラそのものではなく、ハンドラ開始の遅延にある場合が多いように見えます。

TBTはLighthouseでシミュレーションできる指標なので、ここからは試行錯誤が効く世界に戻ります。

### ロングタスクという単位

現代のCPUはモバイル端末でもマルチコアが当たり前ですが、ブラウザの多くの処理はシングルスレッド（メインスレッド）で行われます。つまり一度に1つのタスクしか実行できません。タスクは細切れになっていて高速に切り替わるため、人間には同時並行に見えています。

![タスクが順番にメインスレッドを使う様子](https://assets.ideamans.com/miyanaga/images/2024/11/task-flow-diagram.png)

ところが中には、メインスレッドをなかなか手放さないマナーの悪いタスクがあります。一度に50ms以上の処理を行うタスクを**ロングタスク**と呼び、TBTはロングタスクの50ms超過分の合計値です。

![ロングタスクと50msの超過分](https://assets.ideamans.com/miyanaga/images/2024/11/tasks-diagram.png)

確認はPerformanceタブで行います。左上のリロードマークでページを再読み込みしてタイムラインを表示し、`CPU` を `4x slowdown` などにするとロングタスクを検知しやすくなります。右肩に赤い三角マークのついたタスクがロングタスクです。`Bottom up` や `Call tree` で該当するJavaScriptのコードまで辿れます。

### setTimeoutで分解する

ロングタスクは処理自体を軽量化できるのが一番ですが、それは難しいことが多いはずです。そこで `setTimeout` で分解します。

重い処理の続きをコールバックに移すと、いったんタスクを切り上げて他のタスクにメインスレッドを譲れます。

```javascript
a() // 30ms
b() // 20ms
c() // 30ms
// 合計80msでロングタスク化
```

```javascript
a() // 30ms
setTimeout(function () {
  // メインスレッド解放
  b() // 20ms
  setTimeout(function () {
    // メインスレッド解放
    c() // 30ms
  })
})
```

jQueryでも同じ問題が起きます。1つ30msかかるカルーセルの初期化が、ページ内に5箇所あるとします。

```javascript
$('.slider').slider() // 30ms × 5 = 150ms
```

jQueryのDOM操作は一息で実行されるため、5箇所分がまとめて処理されてロングタスクになります。1つずつメインスレッドを解放すれば回避できます。

```javascript
$('.slider').each(function (i, el) {
  setTimeout(function () {
    // メインスレッド解放
    $(el).slider() // 30ms
  })
})
```

サードパーティタグから提供される社外のJavaScriptには、この手が使えません。実行タイミングを遅延させるか、使用をやめるか、という消極的な対応に限られます。

## まとめ

INPはユーザーの環境でのみ計測される指標で、Lighthouseではシミュレーションできません。実態を掴みづらく、試行錯誤も難しい指標です。参考までに、2024年10月時点の主要通販サイト100サイトでは、CLS良好63%・LCP良好68%に対して、INP良好は46%にとどまっていました。他の指標より苦戦している状況が見て取れます。

それでも、内訳を実データで集めれば打つ手は絞り込めます。Input delayが主因ならTBTの削減へ、Processing timeが主因なら該当操作をDevToolsで再現してタイムラインを掘る。順序さえ決まれば、幽霊探しではなくなります。
